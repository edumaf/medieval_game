# Dependency management (Wally)

## What goes where

| File | Committed? | Edit by hand? |
| --- | --- | --- |
| `wally.toml` | Yes | Yes — this is where you declare dependencies |
| `wally.lock` | Yes | **Never** — Wally writes it |
| `Packages/`, `ServerPackages/`, `DevPackages/` | No, gitignored | Never — regenerated by `wally install` |

The lockfile is committed so everyone resolves the exact same versions. CI fails
the build if `wally install` changes `wally.lock`, which means an uncommitted
lockfile cannot merge.

## The three realms

```toml
[dependencies]         # → ReplicatedStorage.Packages   — client and server can see it
[server-dependencies]  # → ServerScriptService.ServerPackages — server only
[dev-dependencies]     # → ReplicatedStorage.DevPackages — never in a production build
```

Put anything the client must not read in `server-dependencies`. Put test-only
tooling in `dev-dependencies` — `build.project.json` does not map `DevPackages`,
so it cannot ship.

## Adding a dependency

Before you add anything, answer these in the PR:

1. What does it do that we cannot do in fifty lines?
2. When was it last released, and by whom?
3. What does it pull in transitively?
4. Which realm does it belong in?

Then:

```bash
# 1. Find the current version at https://wally.run
# 2. Add it under the right realm in wally.toml, pinned exactly:
#      Signal = "sleitnick/signal@2.0.1"
wally install
rojo sourcemap default.project.json --output sourcemap.json
wally-package-types --sourcemap sourcemap.json Packages/
```

That last step matters. Wally strips exported types from the link files it
generates; `wally-package-types` puts them back. Skip it and the package
resolves to `any`, which silently disables type checking anywhere you use it.

> ⚠️ **`wally-package-types` is not idempotent.** It rewrites link files in
> place, so running it twice on the same folder fails with
> `'REQUIRED_MODULE' is not a function call`. That is not a broken install — run
> `wally install` to regenerate the link files, then run it once more. Always
> pair the two commands in that order. CI does the same, and deliberately does
> not cache the `Packages` folders for this reason.

Commit `wally.toml` **and** `wally.lock` together.

## Updating dependencies

```bash
wally update            # everything
wally update Signal     # one package
```

Then re-run the sourcemap and `wally-package-types` steps, run the full
validation suite, play-test in Studio, and open a `chore/` PR with the lockfile
diff. Never update dependencies inside a feature PR — the diff hides real
changes and makes a bad update impossible to bisect.

## Removing one

Delete the line from `wally.toml`, run `wally install`, commit both files.

## Things that go wrong

**`wally install` fails with a resolution error.** Two packages want
incompatible versions of a shared dependency. Check which, and either relax a
version or drop one of them.

**`wally.lock` conflicts in a merge.** Do not hand-edit it. Take `main`'s
version, then re-run `wally install`:

```bash
git checkout --theirs wally.lock   # during a rebase onto main
wally install
git add wally.lock
```

**A package's types are `any` in your editor.** Re-run the sourcemap and
`wally-package-types` steps above. This is the single most common cause.

**`Packages/` looks stale.** Delete it and run `wally install` again. Nothing in
those folders is precious.
